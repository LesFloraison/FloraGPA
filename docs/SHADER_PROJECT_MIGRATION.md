# Native multi-file shader projects

The Shader page's **Shader Project** action opens the recovered multi-file HLSL
workflow in Qt. Sources and Settings occupy separate tabs; the toolbar selects
the root source and provides Compile & Apply, Save JSON and Import JSON. Settings
retain the original JSON representation for entry, profile, compiler flags,
defines and virtual include directories. Source files can be selected, added and
removed. Unedited source bytes, including CRLF, survive a save round trip.

This migrates `shader_project.py` and `shader_project_ui.py`. Shared shader,
experiment, session and application modules still have other migration work.
It does not implement a new compiler, decompiler or capture format.

## Native behavior

- Project schema validation, canonical SHA-256, captured `/D` parsing and source
  recovery use native C++. Windows virtual paths normalize separators, dot
  components, drive/UNC roots and full Unicode case folding. Ambiguous
  drive-relative paths, duplicate files/macros, unknown settings and unresolved
  captured defines fail explicitly. A recovered multi-file draft requires the
  user to select its root, as in the original.
- `ID3DInclude` reads only the project's saved file texts. Local includes search
  their actual parent, configured directories and the root directory in order;
  system includes skip the parent directory. Each open retains a separate
  buffer until Close. There is no filesystem fallback. The original 16 MiB
  source, 1,024-file/macro, 256-directory/active-include, 4,096-open and 128 MiB
  aggregate include limits are retained.
- Compilation explicitly loads System32's D3DCompiler 47, matching the Python
  reference even when Qt deploys an older DLL under the same filename. Legacy
  `NO_PRESHADER` is removed from the invocation while the project retains its
  requested flags; the compilation report records that removal.
- Projects use the original `source_language=hlsl_project` and `source_project`
  experiment fields. Undo, redo, save/load and later single-file replacements
  preserve or invalidate provenance according to the latest active shader edit.
- Reopening a saved project recompiles it in the worker and checks every
  non-debug DXBC chunk. A mismatching project is reported unavailable. Compile
  failures leave the current experiment intact. A draft tied to a different
  frame, shader or experiment cannot apply; it can still be exported.

The standalone command is:

```powershell
FloraGPA.Cli.exe compile-project capture.gpa_frame --id 27 --source project.json --out result
```

Optional `--experiment` selects the current edited shader for stage validation.
Outputs include `replacement.dxbc`, `replacement.asm`, `shader_project.json` and
`report.json`. Assembly uses the original hexadecimal-literal disassembly mode
and Windows CRLF. `shader --experiment ...` exports the effective shader and
verifies/exports saved project provenance. Resource IDs in the new compilation
report retain uint64 precision.

## Validation

- `tools/validate_shader_project.py` executes the preserved Python implementation
  against the native model: **2,057 cases, including 263 rejected inputs**. This
  includes Windows/Unicode paths, macro quoting and whitespace, schema/defaults,
  byte/character limits, include search/lifetime/recursion, all six shader
  stages, original GPA three-file sources and rejection of incorrect provenance.
- The packaged native CLI is compared with original `analyze.py` for captured
  debug and release projects. Compilation reports, stage/linkage metadata,
  project JSON and assembly bytes agree. Release DXBC is byte-identical. Debug
  comparison checks every non-debug chunk and the complete decoded embedded
  source/environment: PDB GUID/time data generated by D3DCompiler is not claimed
  byte-identical across compilations. Both implementations independently verify
  the resulting bytecode against the project.
- The model suite has 10 passing Qt cases; the integrated UI suite has 7, with
  no skipped cases when the original fixtures are configured. Tests exercise
  actual worker compilation, pixel changes, failed compilation, undo/redo,
  reopen, stale drafts, import/export and experiment reload. The original GPA
  sample reproduces its captured image and the expected edited pixels on both
  hardware and WARP.
- GUI screenshots are generated by the actual Qt widgets, not mockups.
- Full Release build and seven relevant CTest suites pass, including all 54
  original main-window cases. The shipping package passes its 10 model and 7 UI
  cases with Windows-only PATH, four GF2/BF1 golden/negative replay comparisons,
  and nine runtime module audits. No Python/Tk/GPA/RenderDoc module is loaded;
  Qt comes from the package and project compilation uses the system compiler.
  All four shipping executable hashes match the Release build. This is a test
  on this host, not a claim of validation on a separate clean Windows machine.

The reproducible model/CLI comparison command is:

```powershell
python tools/validate_shader_project.py --reference D:/CDXrepo/FloraGPA --probe out/FloraGPA-shader-project/FloraShaderProjectTests.exe --qt-bin out/FloraGPA-shader-project --cli out/FloraGPA-shader-project/FloraGPA.Cli.exe --out artifacts/shader-project-check
```

The test executable and Qt6Test.dll are copied into a package only for validation
and removed before delivery. Python is a development oracle; the application,
worker and project compiler never launch or load it.

The first model comparison exposed Windows UTF-16 path splitting and Python's
base-zero integer syntax differences; those were fixed and the original failed
evidence is retained. Debug DXBC initially differed only in generated PDB data;
the final check explicitly compares non-debug chunks and extracted source data.
An initial integration build also caught a missing compiler-constant include;
the final Release build and tests above use the corrected sources.
